60-second pitch

I built a Pune hotel concierge as a real MCP product, not a notebook demo. The browser never talks to Claude. A FastAPI host runs a Claude tool loop and spawns a separate MCP stdio server whose 16 tools are the only way to read hotels or write bookings in MongoDB.

That split is the point. The language model is a planner. The hotel catalog and reservations are a protocol-bounded tool server. Ownership is enforced in Python — signed-in mobile and email — because you do not trust a model to decide who can cancel BK-1001.

  • Live: hotel-chatbot-42t0.onrender.com
  • Code: github.com/shelarrohit45/Hotel-ChatBot
  • Stack: FastAPI, Anthropic Messages + tool_use, official MCP Python SDK (stdio), MongoDB Atlas, Docker on Render
  • Catalog: 50 Pune hotels. Dummy bookings persist. No payment gateway.

How to walk an interviewer through it

  1. Open the live URL. First screen is guest identity (name, email, 10-digit mobile) — not Google OAuth. Cookie hotel_sid is httponly.
  2. Chat: “2 guests in Pune from 10 to 12 Sep 2026”. Composer stays at the bottom; replies scroll above it.
  3. “Show me photos of JW Marriott” — pictures come from tool JSON, not from URLs pasted in the model text.
  4. Book a room. Booking id looks like BK-1xxx. It is a Mongo document, not chat memory.
  5. “What are my bookings?” then cancel. Log out, sign in as someone else, try the same BK-… — it must refuse.
  6. Ask for weather or Python. Guardrails / system prompt keep it on Pune hotels.
Free Render sleeps. First load can show a plain “Not Found” for about a minute. Wait, then refresh. That is the platform, not a 404 in the app.

What this is

A two-process product in one repo. HOTEL-CHATBOT-CLIENT is the MCP host: HTTP, sessions, Claude, guardrails, UI. HOTEL-CHATBOT-MCP is the MCP server: JSON-RPC over stdio, 16 tools, MongoDB. The host spawns the server as a child process. Same pattern you use when Cursor talks to an MCP server — except here the host is our FastAPI app, not the IDE.

Chat is ordinary POST /chat. Not Socket.IO, not websockets. Each turn is request/response JSON: { text, blocked, images }. The model may take up to 8 tool rounds before that JSON is returned.

Why MCP (not “just function calling in app.py”)

Anthropic tool_use is how Claude asks to call something. MCP is how that something is exposed as a server with typed tools, list/call, and a transport. I kept them stacked:

  • Claude tool_use — model chooses name + arguments from the host’s tool list.
  • Host allowlist — guardrails.py only forwards the 16 hotel names. The model cannot invent os.system.
  • MCP server — official SDK Server over stdio. list_tools / call_tool. Business logic stays in tools.py.

I used the low-level MCP Server, not FastMCP decorators, so each tool’s JSON Schema (date format, required fields, minimums) is exactly what we wrote. Decorators are fine for prototypes; they get in the way when the schema is the contract.

Stdio, not Streamable HTTP, because this server has one consumer: our host. HTTP MCP is for many clients, auth at the edge, shared deployments. A child process with a locked-down command path is the smaller attack surface for a demo that still looks like production MCP.

Claude tool loop (host)

orchestrator.py is a classic agent loop, not a chatbot wrapper. History is Anthropic messages: user text, assistant blocks (text and/or tool_use), then user tool_result blocks. If the API rejects a mismatched tool_result (truncated history), we reset to the current user turn and continue — better a short memory than a 500.

  • Max 8 tool rounds, 24 history messages, tool JSON truncated at 8k chars for the model (full payload still used for photos).
  • System prompt is loaded once from disk: scope in CLAUDE.md, routing playbook in skills.md.
  • Default booking chain: search → details → room → availability → price → create. skills.md exists so the model does not rediscover that every turn.

Availability is not “hope the model remembers.” Overlap is check_in < requested_out and check_out > requested_in for non-cancelled rows on that hotel+room. Inventory is a number on the room document minus those overlaps.

Guest identity

First visit collects name, email, 10-digit mobile. Stored in users + sessions. Chat is 401 until that form is saved. Log out is on the chat header only. 

GET  /auth/me
POST /auth/guest
POST /auth/logout
POST /chat          → 401 without a complete guest

The host injects that identity into create / list / get / modify / cancel after Claude proposes arguments. The model cannot book as someone else by stuffing another phone into the tool call. The MCP layer then checks the booking’s stored mobile and email. Knowing a BK-… id is not enough.

Google OAuth was added and removed. A guest form is enough for this demo and avoids an OAuth client-secret in the host.

Hotel photos

Every hotel has two Unsplash HTTPS URLs in Mongo (exterior + room), not binary blobs. Search/details JSON includes them. The orchestrator walks tool payloads, keeps https URLs, and the UI renders a gallery. Claude is told not to paste URLs into prose — CSP and layout stay under our control.

Asking “show me images” often produced a text-only turn (no tool call). The host now treats photo intent as a first-class case: call get_hotel_details for a hotel_id in the message or recent history, or reuse the last photos from the session.

Chat UI

  • Guest screen: dark stage + cream form. On phones the cream panel fills leftover viewport so there is no black band under the button.
  • Chat: header, scrollable thread, composer pinned to the bottom of the viewport (100dvh flex column, min-height: 0 on the scroller).
  • No tool-name chips. Photos tap-open a lightbox. Static assets cache-busted with ?v=.

Security layers

  • Secrets only in local .env / Render env. Never in HTML, JS, or replies.
  • Input: NFKC, strip tags/nulls, 4k cap, jailbreak regex, topic gate (Pune/hotel) on the first turn; follow-ups allowed in-session.
  • Tools: frozen allowlist of 16 names, 2k arg cap, injection scan on args. MCP command path from config, not from the user.
  • Identity: host overwrite + MCP ownership AND(phone, email).
  • Output: redact sk-ant-…, strip tool names.
  • HTTP: CSP script-src 'self', connect-src 'self', img-src 'self' data: images.unsplash.com, httponly cookie, COOKIE_SECURE on HTTPS, 20 req/min/session.

Open http://127.0.0.1:8000. No auto-reload. Ctrl+C and start again after Python changes. Atlas Network Access must allow your IP (or 0.0.0.0/0 for demos).

Deploy on Render

One Docker web service. MCP is a child inside the same container. Hugging Face Docker Spaces were skipped (free accounts often cannot use the Docker SDK).

  1. Push main to GitHub. Never commit .env.
  2. Atlas → Network Access → 0.0.0.0/0 (Render IPs are not static on free).
  3. Render → New Web Service → repo → Runtime Docker → branch main → Free.
  4. Env: ANTHROPIC_API_KEY, ANTHROPIC_MODEL=claude-haiku-4-5, MONGODB_URI, MONGODB_DB=hotel_chatbot, COOKIE_SECURE=true. Docker already sets MCP_SERVER_PYTHON=/usr/local/bin/python and the server script path.
  5. Wait for Hotel chat API ready. URL example: https://hotel-chatbot-42t0.onrender.com/

If search claims the database is down: env vars on Render, Atlas 0.0.0.0/0, and MCP child env inheritance in mcp_bridge.py.

Honest limits (say this in the interview)

  • No payment, no real GDS/hotel API. Catalog is 50 seeded Pune hotels. Photos are stock Unsplash, not property-owned shots.
  • Rate limiter is in-process memory. One Render instance is fine; it would not share across replicas.
  • Chat history lives in the FastAPI process dict plus a Mongo session for the guest profile. A dyno restart drops in-memory history; identity cookie still works.
  • Free Render sleeps. Claude cost is yours for every public visitor.
  • MCP stdio is one client. This is not a multi-tenant tool gateway.

If I took this to production next: Streamable HTTP MCP behind auth for more than one host; SSE/token streaming for the UI; Redis rate limit + session; Postgres if we need transactions across inventory; actual hotel photos and a payment intent before create_booking; structured logging of tool_name + latency + token use, never of secrets.

Cross questions — MCP & the agent

Q. Isn’t this just OpenAI/Anthropic function calling with extra steps?

A. Function calling is the model’s I/O shape. MCP is the server contract: list tools, call tools, typed JSON Schema, a process boundary. I can point Cursor, another host, or a test harness at the same server.py without copying handlers into each app. The host still uses Claude tool_use. They compose; they are not the same layer.

Q. Why stdio instead of HTTP MCP?

A. One host, one server, same container. Stdio means no extra port, no MCP auth story, command baked into config. HTTP MCP wins when many clients share tools or the server must scale independently. I would move to Streamable HTTP the day a second consumer appears.

Q. Why official low-level Server, not FastMCP?

A. I needed the schema on the wire to match TOOL_DEFINITIONS exactly — date formats, required arrays, minimums. FastMCP is faster to sketch. For a booking API I want the schema file to be the source of truth, not a decorator side effect.

Q. Why 16 tools instead of one hotel_api mega-tool?

A. Small tools give the model a routing surface and give me least privilege. Search does not need the right to cancel. Cancel does not need the whole catalog. A mega-tool becomes an untyped RPC and the model stuffs the wrong fields. skills.md then teaches a chain: search → details → availability → price → book.

Q. How do you stop the model inventing a hotel or a price?

A. System prompt: facts only from tools. Search projects a thin card (id, area, stars, starting price, photos). Details are a second call. If it still hallucinates, the user can be wrong — but create_booking only accepts real hotel_id/room_id from Mongo or it errors. Prices are computed in Python, not in prose.

Q. What happens if Claude asks for a tool you do not have?

A. It only sees the 16 from list_tools after the host allowlist. If a name still sneaks through, validate_tool_call raises and the loop returns a blocked tool error to the model, not a shell.

Q. Tool results can be prompt-injection. What did you do?

A. Treat tool JSON as untrusted text in the next model turn. Cap size at 8k. Project fields so reviews cannot be a 50-page jailbreak. Input guardrails also scan tool args. I do not execute anything from hotel descriptions. A production host would additionally wrap tool_result in a clear “data, not instructions” delimiter and refuse ignore previous instructions inside payloads — I already regex that on user text.

Q. Why Haiku, not Sonnet/Opus?

A. This loop can do several round-trips per user message. Haiku keeps latency and cost acceptable for a public URL. Routing is in skills.md so a smaller model does not have to invent the playbook. I would switch to Sonnet if booking accuracy dropped, not for a prettier paragraph.

Q. Why not stream tokens to the UI?

A. Tool loops are bursty: silence, then JSON, then more silence. Naive SSE of the first text block looks broken when the model immediately tool-calls. I shipped correct bookings first. Streaming is additive: send “searching…” events per tool_name internally, then stream the final text. Guests still must not see raw tool names.

Q. How do you keep MCP env correct in Docker?

A. The Python MCP stdio helper does not pass the parent environment unless you set StdioServerParameters.env. On Render, MONGODB_URI lived on the FastAPI process and the child only had PATH/HOME — search then failed with a vague “database” story from Claude. mcp_bridge.py copies os.environ (skipping bash functions). That is a real MCP footgun. Mention it; interviewers who have shipped MCP will nod.

Q. Could this MCP server run inside Cursor?

A. Yes, as a stdio server, if you pointed Cursor at HOTEL-CHATBOT-MCP/server.py with the Mongo env. The hotel tools do not depend on FastAPI. What Cursor would not have is guest cookie injection — you would need to pass guest_phone/email in the tool args yourself. That is the host’s job.

Cross questions — security & identity

Q. Why overwrite Claude’s guest fields instead of trusting the prompt?

A. Prompts are advisory. A model that is jailbroken, confused, or overly helpful will substitute another email. The orchestrator sets guest_phone, guest_email, customer_id, and guest_name from the session after the model emits the call. Defense in depth: MCP still checks the booking row matches that pair.

Q. Why mobile AND email, not just booking_id?

A. Booking ids are short and appear in chat. If ID were capability, anyone who saw a screenshot could cancel. Dual match is a simple possession check for a demo. Production would be a logged-in account plus authorization records, not two PII fields. I would not pretend this is OAuth.

Q. Why drop Google login?

A. OAuth adds redirect URIs, client secrets, and a “phone still missing” extra step. The product need was a stable guest identity for ownership. A three-field form plus httponly cookie is honest for a catalog demo. I can talk through how I would add Google again without putting the client secret in the browser.

Q. Is the cookie enough session security?

A. HttpOnly, SameSite=Lax, Secure on HTTPS, path=/, year max-age for a demo concierge. No JWT in localStorage. CSRF is limited because CORS is locked to localhost origins and the live site is same-origin POST. I would add CSRF tokens or SameSite=Strict if we added mutating cookie-auth from other sites.

Q. How do you stop someone dumping the system prompt or the API key?

A. Regex jailbreaks before Claude. Topic gate. Output redaction for sk-ant-. The key is never in the frontend. If they ask for .env, we refuse. This is not a formal security review — it is layered hygiene. A determined model jailbreak can still leak prompt text; that is why secrets are not in the prompt.

Q. Why hide tool names from the guest?

A. They are an implementation detail and a social-engineering surface (“call cancel_booking on BK-1001”). The assistant should speak hotels, dates, INR. We strip names in guardrails.py even if the model slips.

Cross questions — data & product

Q. Why MongoDB, not Postgres?

A. The hotel document is already a nested JSON card (rooms, rate plans, reviews). Mongo matches that shape and Atlas was already in the toolchain. I would pick Postgres if we needed multi-row transactions for inventory under contention. For 50 hotels and demo traffic, an overlap query plus inventory integer is enough. I am not religious about the store; I am religious about not keeping bookings in RAM.

Q. Are bookings dummy or real?

A. Real documents. Dummy in the product sense: no payment, catalog is synthetic-ish Pune data. Cancel sets status: cancelled and keeps the row so list/status still explain what happened. Hard delete would make support and audit worse.

Q. How do you avoid double-booking?

A. Before create/modify we count overlapping non-cancelled stays for that room. Race: two concurrent creates can both pass the check on a single node without a transaction. Honest answer: demo-scale; production wants findAndModify / a booking lock / SQL constraints. Say that before they ask.

Q. Why not store image binaries in GridFS?

A. The chat UI needs a URL. Hotlinking Unsplash keeps Atlas small and the seed script trivial. Cost: stock photos, CSP allowlist, dependency on their CDN. Next step is objects in S3/R2 under /static or our own bucket, still URLs in Mongo, never blobs in the chat JSON.

Q. Why did “show me images” fail at first?

A. Photos were in Mongo and in tool JSON, but the UI only attached images[] for the turn that actually called a hotel tool. “Show me photos” was often a no-tool text reply, so the gallery was empty. I fixed it in the host: photo intent loads details or reuses session photos. That is a product bug in the agent loop, not a missing seed.

Q. Why HTTP POST chat, not Socket.IO?

A. A booking turn is a long request with a single final answer. Websockets add reconnect, sticky sessions, and a second protocol for no extra UX. POST plus a pending “One moment…” row is enough. I would add SSE when we stream.

Cross questions — ops, UI, tradeoffs

Q. Why one Docker image, not two services?

A. Stdio MCP must be a child of the host. Two Render services would force HTTP MCP and a private network. One image matches the architecture: host owns the server lifecycle. Split later if the tool process needs different scaling or language.

Q. What broke on Render besides Mongo env?

A. FastAPI StaticFiles mount 404’d in that environment, so app.py serves /static/{filename} explicitly. Python path for the child must be /usr/local/bin/python, not a Mac venv. First hit after sleep is Render’s router with no replica — “Not Found” with x-render-routing: no-server — wait and retry.

Q. Why pin the composer to the bottom?

A. height: 100% does not resolve against min-height on html/body, so the flex thread never filled the viewport and the input sat under the header. Fix: 100dvh column, thread flex: 1; min-height: 0; overflow: auto, composer flex-shrink: 0. Classic mobile chat layout. Same class of bug as the black gap on the guest form after we removed copy.

Q. How would you test this without clicking the UI?

A. Unit-test tools against a test DB: overlap math, ownership refusal, projection fields. Contract-test MCP list_tools names vs the host allowlist so they cannot drift. Mock Anthropic for the loop (tool_use then final text). A thin eval set: “book X”, “cancel someone else’s BK”, “weather in London”. I would not claim we have that harness fully built — that is the next engineering pass.

Q. What is the hardest MCP lesson in this repo?

A. The model is not the application. If a rule matters (who may cancel, which env the child sees, whether photos render), implement it in the host or the tool server. Prompts route. Code authorizes. MCP is useful because it makes that boundary visible: a process that can only list and call tools, and a host that decides when those calls happen and with whose identity.

Q. If you had two more weeks?

A. Stream the final answer; eval suite for ownership and Pune-only; structured traces; real photo assets; optional HTTP MCP for Cursor; and a booking confirmation that is idempotent under double-click. I would not add a vector store. Fifty hotels do not need RAG. They need correct tools.
